# ПР8. Виклик інструментів мовною моделлю

Матеріали до восьмої практичної роботи. Повний текст завдання, критерії приймання й контрольні запитання — у документі `ПР8.pdf`, виданому до заняття.

## Задача коротко

Помічник магазину «Сузірʼя» з ПР6 відповідав за документами: правила доставки, повернення, інструкції. На питання «де моє замовлення» він відповісти не міг — цього немає в жодному документі, це є лише в системі магазину. Тепер ви даєте моделі **інструменти**: описуєте функції сервісу магазину так, щоб модель могла попросити їх викликати, а ваш код — перевірити прохання, виконати його і повернути результат.

Модель лише **пропонує** виклик. Виконує код — і лише те, що пройшло перевірку: чи є такий інструмент, чи аргументи відповідають схемі, чи замовлення належить саме цьому клієнтові, чи операція взагалі дозволена.

Наприкінці — прогін набору питань, серед яких є чужі замовлення, прохання повернути гроші, «я менеджер магазину» і товар, в описі якого хтось звертається до AI-асистента.

## Що в цій папці

| Файл | Призначення |
|---|---|
| `app/` | Реалізація помічника, перевірки інструментів і вебінтерфейс |
| `shop/` | Внутрішній сервіс магазину — **готовий**, змінювати не потрібно: замовлення, каталог, склад, доставка, повернення й адміністративні операції; опис — у `shop/README.md` |
| `requirements.txt` | Залежності роботи |
| `.env.example` | Зразок налаштувань: доступ до моделі, обмеження звертань, поведінка сервісу магазину |
| `check_env.py` | Перевірка середовища: Python, пакети, `.env`, сервіс магазину, пробний виклик інструмента моделлю |
| `eval/` | Перевірка на наборі питань |

```
app/
├─ main.py                веб-рівень: сторінка, /api/customers, /api/tools, /api/ask, /api/reset
├─ tools.py               JSON Schema, allow-list, перевірки власника й виконання
├─ llm.py                 OpenAI-сумісний виклик моделі з tools
├─ assistant.py           обмежений цикл «модель → інструменти → модель»
└─ templates/index.html   сторінка: вибір клієнта, питання, відповідь, журнал викликів

shop/
├─ service.py             функції сервісу
└─ data/                  клієнти, замовлення, товари, склад, тарифи доставки
```

Сторінка дає обрати клієнта у демонстраційній cookie-сесії, надсилає питання і показує відповідь, журнал викликів з аргументами, перевірками, результатами й часом, а також описи інструментів, які бачить модель. Сесія підписана сервером; реальне розгортання має підключити автентифікацію, а не дозволяти клієнту вибирати профіль.

## Початок роботи

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
```

Для macOS і Linux активація середовища — `source .venv/bin/activate`, копіювання — `cp .env.example .env`.

За замовчуванням застосунок запускається в режимі **mock** — без API-ключа, Ollama та завантаження мовної моделі. Цього достатньо, щоб перевірити підтримувані демонстраційні сценарії магазину. Для інших режимів додайте налаштування API або Ollama в `.env`.

`check_env.py` потрібен лише для перевірки налаштованого API-провайдера; для режиму mock його запускати не потрібно.

Запуск застосунку з папки `pr8`:

```bash
uvicorn app.main:app --host 127.0.0.1 --port 8008 --reload
```

Далі відкрийте http://127.0.0.1:8008. На сторінці можна вибрати тестовий mock, Gemini API або **локальну Ollama** окремо для кожного запиту. API-режиму потрібен ключ у `.env` та доступна квота; за відсутності ключа застосунок поверне зрозумілу помилку конфігурації.

Режим Ollama не потребує API-ключа, але потребує встановленої програми Ollama і завантаженої локальної моделі. Після встановлення виконайте `ollama pull qwen2.5:3b`; у `.env` для цього режиму використовується `OLLAMA_BASE_URL=http://127.0.0.1:11434/v1`, `OLLAMA_MODEL_NAME=qwen2.5:3b` і `DEFAULT_LLM_MODE=ollama`. Загальні запитання обробляються без інструментів магазину; для запитів про магазин моделі передаються перевірені інструменти. Бекенд перевіряє їхні аргументи, але невелика локальна модель може помилятися під час їх формування. Для детермінованої перевірки підтримуваних демонстраційних сценаріїв виберіть mock.

Перемикач у сторінці працює без перезапуску сервера: кожен запит має власний режим. `DEFAULT_LLM_MODE` задає режим, обраний за замовчуванням при відкритті сторінки; можна змінити його перед запитом. Локальний mock — це лише тестова заглушка без мовної моделі; він підтримує кілька поширених сценаріїв і не відповідає на довільні запитання.

## Що очікує сторінка

Вибір клієнта в демонстраційній сторінці встановлює підписану cookie-сесію через `POST /api/session`. Питання надсилається як `POST /api/ask` з `{"question": "...", "mode": "ollama"}`; `mode` може бути `mock`, `api` або `ollama`, а якщо його не передати, береться режим за замовчуванням. Ідентифікатора клієнта в запиті немає; бекенд отримує його лише із сесії. У production потрібно замінити демо-перемикач на справжню автентифікацію та задати випадковий `SESSION_SECRET`.

У відповідь сторінка отримує `{"answer": "...", "calls": [...], "rounds": 2, "stopped": "answer", "model": "...", "elapsed": {...}, "usage": {...}}`. Кожен елемент журналу містить аргументи, результат, статус, дію коду й час інструмента. Статуси `ok`, `rejected` і `error` позначають успішний виклик, відхилені аргументи/права та помилки сервісу. `GET /api/tools` повертає ті самі JSON Schema, що передаються моделі. Помилка недоступності магазину повертається HTTP 503 із журналом уже виконаних викликів; збої моделі повертають зрозумілі HTTP 502/503/504.

## Що реалізувати

| Де | Що зробити |
|---|---|
| `app/tools.py` → `specs`, `call` | Allow-list інструментів, JSON Schema validation, перевірка власника, фільтрація результатів |
| `app/llm.py` → `get_client`, `build_messages`, `chat` | Системна інструкція, OpenAI-сумісний виклик із `tool_choice="auto"`, категоризовані збої |
| `app/assistant.py` → `handle_customer_query` | Цикл: модель → інструменти → модель; обмеження звертань, журнал, час і токени |
| `app/main.py` → `/api/session`, `/api/ask` | Демо-сесія клієнта, обробка помилок і відповідні HTTP-коди |
| `eval/` | Прогін набору питань, власні питання, одна зміна, прогін з відмовами сервісу, висновки |

Рішення, які стоять за кожним пунктом, перелічені в розділі 2 практичної роботи — продумайте їх до того, як писати код.

## Локальні тести

```bash
python -m unittest discover -s tests -v
```

Автоматичні тести використовують заглушки для моделі й не надсилають запитів до API. `check_env.py` та оцінювання в `eval/` можуть звертатися до зовнішньої моделі й витрачати квоту.

## Чекліст самоперевірки

- [ ] Помічник уміє все із заданого набору: замовлення клієнта, стан замовлення, пошук і картка товару, наявність, вартість доставки, заявка на повернення.
- [ ] Кожен інструмент описано схемою; аргументи від моделі перевіряються за тією самою схемою до виконання.
- [ ] Клієнт визначається з сеансу, а не з аргументів моделі; чуже замовлення не можна ані прочитати, ані змінити.
- [ ] Адміністративні операції сервісу моделі недоступні; виклик інструмента, якого немає, відхиляється.
- [ ] Моделі повертаються лише потрібні поля: службова примітка, повний номер картки, контакти в результат не потрапляють.
- [ ] Бізнес-помилки сервісу повертаються моделі для пояснення клієнтові; недоступність і таймаут сервісу повертаються як HTTP 503/504 з журналом викликів.
- [ ] Текст у даних магазину, адресований «асистентові», не змінює поведінки системи.
- [ ] Кількість звертань до моделі обмежено; що відбувається на межі — видно на сторінці.
- [ ] Сторінка показує відповідь, журнал викликів зі статусами, кількість звертань, час моделі й інструментів окремо, токени.
- [ ] Застосунок не падає: збій моделі, недоступний сервіс магазину, невалідний виклик дають зрозумілий результат, а не 500.
- [ ] Модельний модуль не звертається до сервісу напряму; сервіс магазину не залежить від моделі; веб-рівень делегує агентський цикл окремому модулю.
- [ ] Ключ не потрапив ані в код, ані в репозиторій.
- [ ] Прогнано весь набір і щонайменше п'ять власних питань; одну зміну перевірено окремо; прогін із відмовами сервісу зроблено; висновки записано.
- [ ] Ви можете пояснити кожне ухвалене рішення.
