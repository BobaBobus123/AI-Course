# ПР7. Мультимодальний аналіз і структуроване вилучення даних

Матеріали до сьомої практичної роботи. Повний текст завдання, критерії приймання й контрольні запитання — у документі `ПР7.pdf`, виданому до заняття.

## Задача коротко

Постачальники надсилають магазину «Сузірʼя» рахунки на оплату — сканами, фото з телефона, знімками екрана. Бухгалтерія переписує з них реквізити й суми в реєстр платежів. Ви будуєте застосунок, у якому це робить **мультимодальна модель**: читає зображення рахунку й повертає заданий набір полів у структурованому вигляді. А далі — те, що робить його придатним для грошей: **код** перевіряє вилучене за схемою і програмними правилами (контрольні суми IBAN і ЄДРПОУ, арифметика рядків і ПДВ, дати, покупець, довідник постачальників) і вирішує, чи можна документ пропустити без людини.

Наприкінці — прогін якісних і навмисно погіршених зразків і відповідь на питання, скільки помилок моделі ловлять ваші правила, а скільки проходять тихо.

## Що в цій папці

| Файл | Призначення |
|---|---|
| `app/` | Веб-застосунок, мультимодальне вилучення, схема, правила й рішення |
| `samples/` | 9 рахунків гарної якості, 18 погіршених варіантів, правильні значення в `expected.json`; опис — у `samples/README.md` |
| `reference/` | Реквізити своєї компанії й довідник постачальників — для правил |
| `degrade.py` | Погіршити зображення самостійно: розмиття, масштаб, контраст, поворот, обрізання, шум, JPEG |
| `requirements.txt` | Залежності роботи |
| `.env.example` | Зразок налаштувань: доступ до моделі, обмеження на зображення |
| `check_env.py` | Перевірка середовища: Python, пакети, `.env`, зразки, пробний запит до моделі із зображенням |
| `eval/` | Запуск оцінювання та збереження сирих відповідей і метрик |

```
app/
├─ main.py                веб-рівень: сторінка та POST /api/process
├─ images.py              перевірка, орієнтація та підготовка зображення
├─ llm.py                 mock або OpenAI-сумісне мультимодальне вилучення
├─ schema.py              Pydantic-контракт реквізитів рахунку
├─ rules.py               програмні перевірки й довідники контрагентів
├─ extraction.py          конвеєр і рішення auto / review / reject
└─ templates/index.html   сторінка: зображення, рішення, проблеми, поля, позиції
```

Застосунок містить конвеєр завантаження й підготовки зображення, мультимодального вилучення, програмної перевірки та рішення `auto` / `review` / `reject`. Сторінка показує результат і причини; помилки формату файла, обмежень завантаження та сервісу моделі повертаються з відповідними HTTP-статусами. Перевірки виконуються кодом і не залежать від тексту, надрукованого в рахунку.

## Початок роботи

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
python check_env.py
```

Для macOS і Linux активація середовища — `source .venv/bin/activate`, копіювання — `cp .env.example .env`.

Ключ доступу перенесіть у `.env` з папки попередньої роботи.

**Запустіть `check_env.py` заздалегідь.** У mock-режимі перевірка не звертається до зовнішнього API. Якщо встановити `MOCK_LLM=false`, вона надішле моделі невелике тестове зображення.

Для запуску без API-ключа встановіть `MOCK_LLM=true` у `.env` (це режим за замовчуванням із `.env.example`) і запустіть застосунок. Mock зіставляє завантажене зображення з навчальними зразками та показує відповідні еталонні дані з `samples/expected.json`; це не OCR і не результат аналізу моделлю. Для зображення, якого немає серед зразків, mock залишає поля порожніми замість показу чужого рахунку. Сторінка показує попередження з результатом зіставлення. Для реального аналізу зображення встановіть `MOCK_LLM=false` і задайте API-ключ та модель.

Щоб оцінити реальне вилучення на 27 наданих зразках, виконайте з `pr7` команду `python eval/run_evaluation.py --run-model`. Вона робить окремий запит до моделі на кожне зображення, тому витрачає квоту; результати, сирий JSON, перевірки й оцінки полів зберігаються у новому `eval/results-<timestamp>.json`. Не запускайте її у mock-режимі — для оцінювання зображень потрібен `MOCK_LLM=false`. `--include-own` додає файли з `samples/own/manifest.json`. Для повного якісного дослідження додайте власне фото рахунку з телефона, вручну звірте його правильні поля, внесіть його в manifest та зафіксуйте висновки за `eval/README.md`; синтетичний degraded-зразок не замінює фото.

Запуск застосунку з папки `pr7`:

```bash
uvicorn app.main:app --reload
```

Далі відкрийте http://127.0.0.1:8000 і завантажте зображення для обробки.

## Що очікує сторінка

Розбір — `POST /api/process` з файлом у полі форми `file`. Успішна відповідь містить `decision`, `reasons`, структурований `issues`, вилучені поля у `data` і виміри/токени у `meta`. Кожна проблема має формат `{"field": "supplier.iban", "rule": "iban_checksum", "message": "...", "severity": "error"}`. Непридатне зображення дає HTTP 400, завелике — 413, а збої чи недоступність моделі — 502/503/504 з поясненням у `detail`. `UPLOAD_MAX_MB`, `IMAGE_MAX_SIDE` та `IMAGE_MAX_PIXELS` обмежують вхідне зображення; назви параметрів LLM у `.env.example` відповідають тим, що читає код.

## Реалізовані компоненти

| Де | Реалізація |
|---|---|
| `app/images.py` | Перевірка формату, розміру файла й кількості пікселів; EXIF; масштабування |
| `app/schema.py` | Pydantic-схема структурованого результату |
| `app/llm.py` | Явний mock-режим або мультимодальний API із перевіркою відповіді |
| `app/rules.py` | IBAN, коди, Decimal-арифметика, ПДВ, покупець і довідник постачальників |
| `app/extraction.py` | Конвеєр та рішення, які обчислює код |
| `app/main.py` | Endpoint та HTTP-помилки для файлів і помилок провайдера |
| `eval/run_evaluation.py` | Платний за квотою прогін моделі з JSON-результатами |

Рішення, які стоять за кожним пунктом, перелічені в розділі 2 практичної роботи — продумайте їх до того, як писати код.

## Чекліст самоперевірки

- [ ] Застосунок приймає зображення рахунку й повертає заданий набір полів; відповідь моделі перевіряється за схемою.
- [ ] Значення, якого в документі немає або якого не видно, повертається як відсутнє, а не вигадується.
- [ ] Правила перевіряють IBAN, коди, арифметику, дати, покупця й довідник постачальників; кожна проблема вказує на поле.
- [ ] Рішення `auto` / `review` / `reject` ухвалює код за результатами перевірок, а не модель; причини показано.
- [ ] Текст у документі, адресований «системі обробки», не впливає на рішення.
- [ ] Сторінка показує рішення, проблеми, поля, позиції, розміри зображення до й після підготовки, час, токени.
- [ ] Застосунок не падає: порожній, завеликий файл і не зображення, збій моделі, невалідна відповідь дають зрозумілу помилку.
- [ ] Модуль зображень не знає про модель, модель — про правила, веб-рівень — ні про що з цього.
- [ ] Ключ не потрапив ані в код, ані в репозиторій.
- [ ] Прогнано всі зразки й щонайменше два власні; порівняно з правильними значеннями по варіантах; пораховано тихі помилки; одну зміну перевірено окремо; висновки записано.
- [ ] Ви можете пояснити кожне ухвалене рішення.
